## 1. 定位、问题与成功标准

### 1.1 定位与目标

**员工表达目标，岗位 AI 综合助理承接整理、核对、关联和跟进，在授权范围内推进至可用结果或明确待人处理的节点。**

服务后勤、行政、人力及其他综合事务。员工少重复填报和查状态，综合部少抄录、转达、对表和追问，执行者收到清楚安排，审批者看到真实事实、依据、变化与待决问题。各功能必须说明帮助谁完成什么准备工作、减少哪项负担及还需要谁作决定，不能以模块数量或自动生成量替代价值。

用户确认综合部实际有两名员工：经理主要安排工作，另一名办理人员执行办理；其下厨师为中国人，清洁工、司机、帮厨等为属地员工。按用户最新要求，产品主工作流以一个“综合经办主体”承接目标和办理，经理安排工作是现实职责，不增加经理到办理人员的审批、强制交接或双岗位系统。一个主体是工作流视角，不是减少实际人数、共用账号、合并真实身份或开放全部权限。避免额外整理、批准和维护负担；执行人员只需获得必要任务和简单反馈入口。国籍与属地身份不能推出使用语言、识字情况、设备、账号或手机操作条件，这些按真实人员核定。

用户确认现有渠道为微信、口头和在线Excel，痛点主诉是“繁琐，就是繁琐”。这是定性说明，尚无具体完整流程、耗时、频次或样本。采用的待验证假设是：经办可能需要从多个渠道整理需求、重复转录和解释、追问缺项及执行反馈；相同人员/行程可能多次填写、变更或实际结果未关联。按第12节核真实过程与净减负，不把这些假设写成已调查结论；UX说明只能用明确标假设的场景，不伪作真实工作记录。

只知道在线Excel这一渠道称呼，尚未核表格平台、权威表/字段、维护人、访问或接口权限。微信也不等于已有发送、读取账号或集成授权；口头信息的代录仍区分陈述人与记录人。方案可先考虑授权文字输入、人工选取材料或引用记录，不宣称渠道已连通，不默认增加其他通信软件。

用户进一步明确必须做成类似Meta Muse的综合部助理，作为核心产品与UX形态硬约束：**目标委托 → 在已授权能力和预算内持续推进 → 透明活动、等待对象与下一步 → 可编辑可用结果 → 用户修改、暂停、继续或接手。** AI承接具体信息工作位于产品主路径，不能将四业务管理门户套一个聊天框作为交付。该形态服务员工私有目标与综合部获授权工作视图；私人聊天不自动共享，也不为每人另建完整系统。

同一事务的上下文保存、事实修订和续办属于核心责任；长期个人偏好记忆、通知通道、具体卡片布局、输入方式与视觉细节按真实需要设计和验证，不把Meta全部功能默认列为必需。Muse式形态不表示接入Meta供应商、复制云电脑/浏览器或多智能体技术，不授权无限持续执行，也不认定参考产品的实际质量；技术由后续架构选择。必要真实审批、执行、签发与确定性程序的边界不因形态改变。

用户后续明确：出行与用餐是独立事项，不以“出行与餐次”作为必选类别。事项入口按后勤服务、行政办公、费用与物资、人员事务及综合事项归组，使用日常业务名称；用餐意见的自愿原则保留在提交行为中，不写成生硬类别名。助理应在获授权上下文中主动发现出行、用餐等事项的可能关联，说明依据与缺项，再提供可修正的建议；不能因类别或计划直接登记真实用餐、批准、派遣或扣餐。此次导航改动不等于自动关联发现已实现。

### 1.2 成功标准与非目标

用户确认当前为竞赛阶段，数据库设计必须轻量、好部署。这是架构约束：仅保留所选持续事项、必要事实/来源、真实身份与权限、独立业务状态、活动和成果续办所需的数据，避免预建覆盖全部业务的大总库；启动过程应简单可复现，模型配置及未配置/未接入状态清楚。具体数据库、服务形态与部署方案由架构提出，不预定表数或技术栈。竞赛演示不免除真实安全审批、最小权限、独立状态、确定性计算与恢复底线；模型候选、演示夹具和实际业务证据继续分开，未测效果不填。

| 成功标准 | 验证口径 | 当前状态 |
| --- | --- | --- |
| 一次事实输入支持同一事务 | 用实际行程核对安全准备、用车、餐次是否引用同一已确认修订；统计重复填写与修改 | 待实现、待验证 |
| 业务决定与实际结果可信 | 批准、派遣、出返、备餐、实供、维修反馈及真实回执有各自来源；未知可见 | 待核合同、待验证 |
| 净减负 | 同人、同任务、同完成目标比较完整耗时，包含补信息、修正、确认、交接、日常维护与模型成本 | 无当前效果数据，不预填比例 |
| 安全与可恢复 | 越权、撤权、取消、并发、部分失败、重试及人工接手满足验收 | 新流程未验收 |
| 能支撑真实交付 | 工程、真实模型、业务核对、实际样本和目标运行环境分别留证；外部验收另按真实适用要求 | 本项目尚未实现、测试、试用或验收 |

非目标：完整 ERP/OA/财务/人事系统、通用流程编排器、全公司督办、自动安全批准、模型裁定制度效力、自动录用/付款/签发、无边界浏览器代办、全网监测，以及用合成数据填满运营看板。物理维修、实际出行、厨师决定、组织审批和正式签发由真实责任人完成。简单计算和状态反馈不为调用 AI 而增加操作。

## 3. 用户、职责与最小权限

业务职责与授权范围从本项目真实人员分工确定，账号角色按实际职责设计。职位、参与同一事务或系统管理身份均不自动获得批准、派遣、证件或源附件权限；查看、编辑、执行、确认及组织批准分别明确授权和证据。

下表描述可兼任的业务职责，不是要求新增岗位或一职责一账号。综合经办主体依实际安排与授权办理调度、维修经办、人事/签证、资料核对等必要工作；经理与办理人员保留真实身份，权限按各人具体范围授予，任务与活动记录真实责任/操作人。经理安排不自动等同安全批准，也不新增经理→办理人员审批层或强制交接。兼任不取消原安全审批人或专业执行者的职责，不自动开放另一人的全部敏感材料。确有代班需要才按授权交接，不共用个人账号或冒记操作人。

并发验收中的不同经办账号用于核权限与冲突处理，不要求日常工作形成两个经办工作盘；同一经办跨端并行操作也须符合恢复和一致性边界。

| 用户/职责 | 可见与可操作的必要范围 | 不自动获得 |
| --- | --- | --- |
| 员工/事务发起人 | 私有对话、本人需求与材料、相关已授权安排；确认本人事实、例外、真实反馈 | 他人证件/休假原因、全项目记录、批准/派遣权 |
| 同行人员 | 本人被列入及获授权同行信息、本人餐次例外与反馈 | 发起人替同行确认全部身份/材料/私人原因；全组附件 |
| 综合部经办人 | 职责内需求、缺项、资源与关联状态；核对来源、处理例外、授权分派与交接 | 跨业务全量人事或护照、自动安全批准、管理员等同业务审批 |
| 原安全审批人 | 原权限内真实行程、审批材料、修订差异；按原渠道批准/拒绝 | AI建议作为批准、未授权扩大审批范围 |
| 调度经办人/司机 | 调度人处理授权资源与安排；司机查看必要乘车/联系、地点时间、派遣并反馈实际出返 | 护照、休假原因、安全审批附件或无关人员材料 |
| 厨师/食堂经办人 | 菜单发布、意见及餐次汇总/变化原因；必要饮食约束；供餐实际反馈 | 全量行程细节、证件、私人聊天；多数意见覆盖个人约束 |
| 清洁工 | 本人获授权清洁任务的地点、范围、可进入时段和必要联系；接单、障碍及实际处理反馈 | 私人聊天、证照、无关员工材料；凭任务获得未授权房间进入权 |
| 帮厨 | 厨师或经办授权的备餐/协助任务、必要数量和操作信息；承接、缺项及实际完成反馈 | 全量行程、个人证件；独立发布菜单、替厨师决定或自动记入出库 |
| 维修经办/执行人/必要验收人 | 职责内地点、问题、分派、接单、处理证据和反馈/验收 | 无关私有附件；以AI摘要代替维修事实或专业验收 |
| 人事/签证等专门经办人 | 已获授权人员字段、材料、办理记录与缺项 | 其他综合人员天然可见、模型决定录用/待遇/通行 |
| 按需资料/规则责任人、系统管理人员 | 对所选资料核来源/适用范围，确认明确规则；管理系统运行和授权配置，职责按实际需求设置 | 强制另设知识管理/制度审核岗位；把资料核对当业务批准；系统管理自动获得全部业务内容 |

共享只包含明确对象与必要内容。指定参与者不等于授予源文件权限；派生摘要、附件、缓存、导出和通知遵守相同权限限制。审批人更换、人员离岗或撤权时，停止未来不具授权的动作，按第10节处理已发生事实与可见内容。

### 4.2 范围和优先级建议

### 4.3 面向综合经办主体与员工的额外候选

| 属地考勤与合同记录核对（F-023已有日常人事、考勤请假与合同期限） | 服务属地员工及获授权人事经办。例：“我的这条考勤与已批准请假记录不一致，帮我整理待核信息。” | 整理授权排班、实际考勤、批准请假及合同原件/变更的差异与缺项，准备本人解释或经办核对清单；合同期限提示保留真实来源。 | 员工反馈本人事实，经办核实际记录，合同决定与签署沿真实责任；模型疑点不作旷工、工资、续聘或处罚结论。少跨表核对、翻合同和反复说明；适用口径/隐私按Q-001/010/011核定，不增打卡维护或自动裁定权益。 |
| 通知公告的定向解释与变化跟进（F-015/018/024已有通知、公文与传播） | 服务获授权员工与发布经办。例：“这份新通知哪些要求与我有关，较上一版有什么变化？” | 从已读获授权原文解释适用对象、要求、时间及不确定项，定位原文和版本差异，准备本人下一步与待问问题；不从标题编内容。 | 发布范围、正式发布与要求效力由真实责任人核定；发送、送达、已读、理解声明、实际落实分别记录。少逐人解释和追问版本；通道沿Q-014核定，原文未读取不称已解释，不因发送或已读称工作落实，变更不静默改批准。 |

选择这些候选前，应核实际归属、现有记录、输入、真人动作与维护成本；按第9.2节补完整场景合同和独立验收后才进入设计开发。没有来源或责任未定时，只做准备或明确待核，不把额外目录数量当减负价值。

## 5. 共用持续助理与信息结构

### 5.1 用户可观察的代办责任

本节是用户确认的核心形态责任，不是四业务门户旁附一个对话窗口的建议。助理应在真实授权和能力内承接、保持和推进同一目标；缺少业务规则、权限、接口或真人结果时明确等待并保留可续办输入，不靠模型持续猜测制造进展。

1. **开始**：直接文字描述、结构化补充或选择授权文件/已有记录；同一目标形成可继续的事务，独立工具可不建完整事务、不强入共享知识库。
2. **理解与确认**：AI提取候选、追问阻断项，保留原话/来源；已确认字段不被静默改写。集中核关键事实与关联影响，简单反馈可直接操作，不为“我已返回”等待生成。
3. **推进**：只执行已授权、已有真实能力的准备/查询/业务动作；按真实事件和确认规则继续。需要本人决定、他人反馈、权限或外部能力时明确等待；不同任务可分别续办。
4. **交付**：事项卡显示目标、事实、来源/版本、各业务状态、缺项、下一步、等待谁、真实安排/凭证及活动。工作结果可为适用说明、行动指导、偏差清单或业务安排，不以正文/模板/导出为统一门槛。
5. **变化与结束**：只重核受影响范围；保存修订及历史，满足场景关闭条件才办结。用户可停止未执行代办、人工接手或重开；停止不自动取消已发生业务动作。
6. **节制**：普通进展合并；只对关键缺项、冲突、期限变化、失败或必要决定请求处理。有限预算和重试，不能无限循环。

需要资料或要求核对时，按任务提供查证、下一步指导或对已有安排/记录的核对，可独立保存；所用能力按当前目标组合，不增加必经步骤。查证在问题查清后结束；指导在可用下一步或待人节点明确后结束，不等于实际执行；核对结果列依据、偏差、未知、未检查和纠正候选，不能核对自己刚生成的清单冒称检查实际工作。软件任务结束、执行者声明、人工核对和正式批准分别显示。

下列六项是后续设计与相应既有AC需可观察的核心形态约束，不新增需求或验收编号，也不是已测试通过记录：

| 约束 | 后续必须能观察的行为 | 关联需求 |
| --- | --- | --- |
| 目标式主要入口 | 用户直接委托真实目标，AI承接具体准备/核对/跟进，必要业务分类为辅助；不先要求遍历管理中心或填写多套表。 | F-001 |
| 同一事项保存与续办 | 对话、已确认事实、所选材料、安排和成果关联同一事项；关闭重开可续办，变更只修受影响内容，不重复填原事实。 | F-002/014 |
| 透明活动与节制打断 | 可见已做、正在做、等谁及原因、下一步；仅关键缺项、变化或决定需打断，普通进展合并，真实反馈到来后可继续同一目标。 | F-002/015 |
| 可编辑可用成果 | 结果可编辑、保存并用于下一步；简单反馈可直接操作，不以长文或导出统一定义任务结束。 | F-017 |

### 5.2 输入、成果与首页

建议首期最低路径为文字和员工确认的结构化事实；授权文件按任务需要选入。新项目尚无已支持格式、上传、解析或识别能力，输入类型由Q-013冻结后开发验证。上传/原件存储、文字读取、内容识别、结构化提取、事实确认分别展示结果；照片附件、图片理解/OCR、语音转写各自待选验，不写成已具能力，不依照片识别才能接单。能存储不等于能读懂，扫描/不可读部分明示未检查；用户可人工补充文字继续。

首页与事务工作区必须使目标委托、正在代办、需我处理、等待对象和可用成果成为主路径；AI目标输入位于主要工作区，对话就地连接可编辑结果，不只在侧栏等待提问，也不让常驻长聊天挤占真实工作。任务例子引导表达实际目标，不把生成报表或文稿作为所有工作的终点。

具体排列建议：项目与身份范围 → “今天需要处理什么”与少量个人常用入口 → 需我处理、缺项/冲突/变化 → 正在代办与等待谁 → 今日真实安排 → 近期结果、交接及常用依据。四业务域作为次级范围导航，未建设模块不做空壳；左侧导航、业务分区和常用入口各承担不同用途，避免反复进入中心才能开始目标。排列和卡片样式可调整，但不能削弱前述核心形态。

同一产品按授权范围提供三种首页任务视图，具体布局均为建议，不另建三套系统：综合经办看“范围 → 目标 → 需我处理 → 代办/等待 → 今日安排 → 近期成果与交接”；员工看“私有目标输入 → 本人事项/待补 → 本人安排 → 菜单及自愿意见 → 报修/清洁 → 保存成果”；执行者看“本人任务 → 地点/时间/范围 → 接单/障碍/处理反馈 → 变更”，厨师按真实职责增加菜单发布和必要餐次。负责人依授权看阻塞与需本人决定事项；各视图不靠职位或共享项目身份扩大内容和动作权限。

综合视图围绕一个综合经办主体组织工作，不另设经理工作盘和办理人员工作盘之间的必经转派/审批；经理提出安排可作为授权目标来源，实际操作者和责任仍各自记录。跨人代班交接按需显示，不是日常每件事务的完成门槛。

计数必须可打开权限内明细，注明口径和时点：待办是本人尚需行动的唯一任务，逾期为子集；待核对与正式待审批分开；未接入/未采集/未知不填0。预计报餐/确认报餐/实供、已派车/实际出车分别统计；多币种不直接合计。天气时钟与品牌图不得占主要操作区；业务统计只能来自可核实记录。

视觉建议吸收参考图的克制蓝白、清晰选中导航、可扫读业务分区、少量常用入口、具体任务例子、近期事项和本人日程，服务Muse式目标与持续代办主路径。欢迎横幅、时钟与宣传图压缩为辅助信息，主区优先真实待处理、缺项/冲突/变化和正在代办；统计只在有实际决策用途且来源可靠时展示，不为填满首页放趋势图。图仅为视觉及业务范围参考，不产生技术、批准或实施决定，也不把产品改为管理门户主导。

桌面主要动作明确；手机单独按目标、本人安排和简单反馈组织，不照搬桌面多栏。键盘焦点、标签、可持续错误提示、加载/空态/失败/无权限/刷新返回均可用。详情不残留上一对象，换账号后此前异步结果不回写。上述方案尚未形成界面、浏览器测试或实际可用性结果。

执行端建议只展示“需要我做什么、在哪里、何时、必要注意事项”，允许简单反馈“已接受/有障碍/已处理”及必要说明；执行者声明与实际结果核对仍分开。司机、清洁工和帮厨不需查看完整部门管理界面或反复填写经办已确认信息；厨师保留真实菜单发布职责。是否采用中文、中英对照、其他语言或语音输入/播报由真实人员语言与操作条件决定，仅为待核方案，当前均不宣称支持。设备、网络、账号/代录方式按Q-010/013核定，代录保留实际反馈人和经办记录人；通知对象及通道沿Q-014，不因属地身份自动采用特定软件或外部发送。

## 6. 出行安全—用车—餐次联动

### 6.1 正常流程与事实

1. 员工说明目标；AI整理发起人/同行、用途地点、计划离营/返营、用车及必要餐次例外，带出有权且当前确认信息。同行事实核对沿现有授权，不新增每名同行的批准/确认层；发起人可依已授权有效来源填写同行必要信息，但不代确认未知敏感身份/材料。具体边界按Q-006，不因一起出行自动共享私人材料。
2. 相对时间转为可确认日期；离营、航班起降、国内/境外时区和返营各有含义，不能混用。缺关键条件明确待补，保留原意及人工更正。
3. 集中确认同一行程修订与联动影响。按原渠道准备安全审批；实际提交、批准或拒绝必须有真实记录/经授权操作，AI不批准或代签。未接入则提供准备内容、原链接或人工引用，不能标自动提交。
4. 调度根据授权资源提出/确认候选安排，校验时间、车辆、司机、人数/座位、维修等明确条件。可以预备资源候选，未经有效安全批准不显示出行可执行；最终派遣由授权人确认。资源口径待Q-004。
5. 按Q-005确认的触发状态和餐次规则派生餐次影响。无需再次提交每餐申请；不确定时显示待核。食堂看必要汇总、变化理由及饮食约束。
6. 实际出发、返回来自获授权真实反馈或可靠接口；计划不能推断实际。实际已出行但没有有效批准等例外仍如实记录，单列安全待处置，不为批准门槛阻止事实登记或补造批准。反馈迟到或不完整保持未知，AI整理但不补造。实际供餐另记真实结果，不从行程推算。
7. 经办按规则核对资源与餐次未解决项，满足6.4关闭条件后办结，保留行程及关联修订。

### 6.2 独立状态与推进依据

状态名称为产品合同，具体与原系统映射由架构前Q项确认；不把一条总“完成”状态替代下列业务。

| 轨道 | 状态/事实 | 谁依据什么推进 |
| --- | --- | --- |
| 行程事实 | 草稿/待补 → 已确认修订；原计划与实际事实分别保存 | 员工/同行授权确认；实际时间由真实反馈/来源登记 |
| 安全审批 | 准备 → 实际已提交 → 真实批准/拒绝；变化后待重核 | 原安全渠道/授权审批人记录，含批准适用修订；没有凭证保持未知 |
| 车辆安排 | 需求/候选 → 已确认派遣 → 实际出返或未执行；取消待确认/已确认 | 调度确认、司机/授权人真实反馈；获批不等于派遣/已出发 |
| 餐次影响 | 预计调整/待核 → 依口径有效调整；备餐/实供分别记录 | 确认规则与当前有效行程/例外计算；食堂登记准备及实际供应 |
| 代办进展 | 可继续/等待事实/等待人/等待能力/失败待接手/已停止 | 可核来源与实际动作结果；已读/提醒/模型回答不作为执行 |

### 6.3 餐次、变更、取消与并发

- Q-005必须确认触发状态、当地饭点/时间口径、截止/冻结、应报人员/单位、适用餐次及例外。一次确认行程及允许联动后按明确口径计算，不能引入逐餐审批。
- 仅能判断该餐预计不在营时派生减餐。部分重叠按已确认明确口径判断，能够判定该餐不在营时可联动；时间未知或口径不足以判断时保留原餐次/标待核，不默认扣餐，也不新增每餐审批。没有应报清单不能认定缺报，没有可靠应报人员/餐次基线时仅显示已确认申报或变化，不生成完整总人数，也不将未知置零。
- 同一员工同一餐次受多条有效行程影响时只计算一次减餐。取消一条行程须核对其余仍有效影响，不能恢复仍由另一条行程应减的餐次；同时保留手工例外，不按行程条数重复减人。
- 手工例外优先，不被自动重算覆盖。明确过敏/忌口只向必要职责可见，不因行程关联扩散。
- 改期/延返/目的地/人员变化形成新修订，重核受影响批准范围、资源和未来餐次。是否重新安全审批依项目规则，未核不能默认沿用旧批准。旧回执不覆盖新修订，也不抹掉当时有效历史。
- 拒绝/取消/重试不重复占车或减人；撤回只恢复本系统派生且尚可调整的未来餐次，保护手工例外和既往实供。截止后已备餐、已供餐、实际车程不回滚删除；显示迟变和差额待处理。
- 取消未执行资源需可靠结果；外部取消未确认时标待确认，不把车辆/司机直接视为已释放。已执行部分保留真实事实，后续按原业务处置。
- 同车/司机重叠安排并发时，不得形成两份都有效的安排；至少一方获明确冲突和重新选择入口。占用时段、共享座位和允许合并口径待Q-004，不预设实现策略。
- 重复表达提示继续原事项或明确新目标；不能因文字相似强行合并不同出行。相同事务重复提交/回执只处理一次，同一修订的异步结果不能覆盖较新确认。
- 审批、派车、餐次某部分失败，显示已成功和待处理部分；重试只处理未完成部分，用户可人工接手，不能统一显示全完成或悄悄撤销已成功实际动作。

### 6.4 关闭条件

准备任务可以在材料可用或待人节点明确时结束，但行程不能因此标业务办结。建议行程关闭须明确最终结果：取消/拒绝且未执行资源和未来派生餐次已按规则处理，或实际出返、安排结果与餐次差异已核对；无遗留待核/待取消项。谁能关闭、未反馈超时及例外移交方式由Q-002/004/005确认。口径未定时保持待核，不自动超时完成。已关闭后新证据可按授权修订/重开，保留原结论及原因。

## 7. 个人维修服务闭环

员工文字描述 → AI代登记并补问必要地点/问题 → 授权经办分派或依已确认责任映射分派 → 执行人真实接单 → 处理中/障碍反馈 → 提交真实处理结果 → 本人反馈 → 原规则需要时专业验收 → 关闭或退回/重开。

- 文字是最低可用路径，不要求上传照片、写审批材料或先建完整事项。简单明确任务不反复确认所有字段；AI补问阻断项，分类和建议不当安全诊断。
- 分派需要真实授权和责任映射；没有映射/例外等待经办，不让模型猜责任人。无人接单可提醒/改派，实际接受独立记录。
- 执行者声明已处理、报修人反馈“解决/仍有问题/未验证”、专业验收分别记录。AI摘要和照片不能证明已修好。
- 关闭条件按Q-007确认：需要专业验收时未验不能关闭；本人未反馈不自动等同解决；迟到反馈/仍有问题可按授权重开。取消、重复报修、拒接、退回、转派、延期和失败有下一步，不能丢历史。
- 沿原必要专业验收，不新增每单主管审批。实质维修已发生时停止AI不删除工单事实。

## 8. 菜单发布与员工反馈

厨师描述/粘贴菜单 → AI整理候选 → 厨师发布/修订 → 每名员工可查看授权菜单并自愿反馈 → AI按日期/菜品归纳真实意见/重复与分歧 → 厨师可回应或采用 → 保留版本及反馈。

- 厨师决定正式菜单，AI生成不等于发布；修订保留原日期/版本，意见不能直接改菜或采购。
- 员工可一句话反馈，无每日强制评价、意见审核或另加批准层。普通阅读/反馈可直接操作，不为AI调用增加等待。
- 汇总可追到实际意见和覆盖范围；少数意见不写成全员意见，重复意见不伪造人数。保留不同声音和明确过敏/忌口，不以多数覆盖个体安全约束。
- 原则上菜单发布和单次意见提交即可结束对应软件任务；意见已处理/回应与下一版菜单采用分别记录，不要求每名员工反馈后才能结束。
- 关联可靠餐次汇总用于食堂安排；备餐预测、配料、库存和采购扩展依Q-008/011及F-020，不通过AI估算自动出入库。

## 9. 休假返岗及后续业务合同

### 9.1 休假—离境—返岗材料准备

复用同一授权人员与旅程：准备休假申请、护照/签证已确认字段、国内真实证明、适用NIS Landing/Exit Card、接送和餐次恢复节点。先交付可编辑准备清单、缺项核对及提醒，外部提交/接口与正式办理分期，必须冻结具体纳入范围。

各材料独立记录未准备、待办理、真实已提交、回执待核/已核、失效/待重核；不同材料不套一个“批准”。提醒发送、本人声明、来源回执核对分开。必须材料未知/缺失时不显示办妥、获准或可通行；AI可以准备说明草稿，不能生成证明、批准、盖章、卡或代码顶替实际签发。航班/身份/要求换版使受影响检查待重核。

准备任务在可用清单或明确待办理节点形成后可结束；旅程/手续办结必须满足实际纳入范围的真实材料、回执和责任人核对，不能由“清单已生成”关闭。接送与餐次复用第6节，不另创建一套行程事实。

### 9.2 独立工具和全业务后续

- 会议：首批用文字笔记/转写；讨论、提议、决定、分歧分别保留。责任、期限来自记录或确认；真实接受/反馈后才称行动承接。ASR不是前置。
- 月季报/收发台账：保留期间、项目/组织、单元格/原位置、单位币种、累计/去重口径。无应报清单不核缺报，缺数不当零；不同项目/期间/数值不静默合并。确认提取值后程序计算，AI解释不代算。
- 舆情/素材：限定授权公开来源与范围，URL内容未读不能凭链接写简报。发布时间/采集时点、事实/观点/分析、冲突和同名误配分开；素材元数据检索不当图片/视频理解，版权未知不判可发布，不承诺全网持续监控。
- 双语/一事多稿：沿用同一事实，不增金额、期限、决定或立场。渠道稿与内部依据分开，人把关正式外发。
- 多人协作：真实账号产生提交/承接/反馈/核对；上传不等于满足要求，分享不等于获源附件权。资料状态可为未提供→已提交→需补/已确认；行动为待接受→承接/处理中→声明完成→结果核对。外部身份、披露和通道另验，不建全公司督办。

第4.3节八项候选和第4.4节六个图中细化方向均沿本节择取，不自动转为已纳入实施需求。若选中印章/单位证照、资产、服务商、费用、考勤合同或公告场景，须分别核真实职责、唯一记录、权限、输入、状态、完成/回执和异常；不能复制出行或维修的批准/关闭条件，不能用共用AC代替尚未补出的场景验收。
