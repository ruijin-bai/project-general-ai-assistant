# 报修与清洁承接合同

2026-10-08 / V0.1，下一切片设计，未实现/未验证。依据[PRD](../product/PRD.md)第7、9.3节，F-008/021、AC-020–021及AC-006–007/019/028–029/035；复用[业务准备合同](业务准备合同.md)和[身份与菜单合同](身份与菜单合同.md)的独立身份、幂等、最小投影与撤权边界。身份菜单正在集成；auth_meta、menu_feedback是实际增量，readshare/旧记录认领尚未实现，本文不把旧设计写成已交付。

## 1. 切片与权限

员工一句话可开始repair/cleaning私有事项，文字最低路径，不强制照片、主管审批、满意度填表或完整材料。员工明确把必要服务信息交给**一个选定综合经办账号**，经办手动选活跃executor分派；executor以本人账号接受/拒接/反馈；发起人可一句话回应。均为本地独立账号软件操作，现场规则未核不阻提交、手动分派和声明记录，不冒称现场派单系统同步、批准或已维修/已清洁。

服务端从当前session取actor，禁止请求指定操作者/本人反馈人。账号admin不自动获得经办、分派、执行或发起人动作；职责可真实兼任但日志始终署同一真实账号，不新增经理→经办审核岗位。模型只能准备文字、缺项和候选，不能调用提交/分派/承接/完结端点。

| 主体 | 允许动作与所见 | 默认无权 |
| --- | --- | --- |
| 发起人（事项owner，employee或实际兼任经办） | 私有原事项；提交必要服务投影；查看自己的服务事件；修订需求、撤回共享、记录本人结果 | 改他人承接/声明、专业验收、替经办分派 |
| 单一选定clerk | 该提交服务投影、事件与独立下一步；手动分派/改派/撤派；记实际代录声明且署代录人 | 私有原文/附件/完整成果、其他员工事项、替executor接受/声明完成、替发起人称解决 |
| 当前executor | 仅当前被分派服务投影；本人承接/拒接/障碍/处理声明 | 原事项/来源/成果/证件、别人的任务与联系方式、改派、改发起人反馈或闭单 |

原事项的 `/api/matters/{id}`、sources、artifact下载仍只走原权限；收到服务投影不获得原事项访问权。clerk/executor都经服务端专用投影入口，其他账号直接ID访问404；有读取权但动作不符403。executor事件投影只含当前epoch的分派、必要修订说明及其本人回应，不给历任executor的私人说明/联系；requester/选定clerk可看本服务完整动作历史，但不能借事件读取私有来源内容。

## 2. 必要字段与信息投影

提交不重新填已有已核字段。发起人点“交给经办处理”时明确选clerk（服务端验证活跃clerk职责）；没有可选经办保持私有准备并显示等待，不默认第一个管理员。location与problem/scope仍缺失时422只问该阻断项；允许先保存私有草稿。派给executor由经办明确选择，不用AI猜职责映射；现场自动责任映射未核时不启用自动分派。

固定投影字段：`domain, location, request_text, access_window, entry_permission, contact, request_kind, notes`。repair的request_text取已确认problem；cleaning取已确认scope。contact只含本次明确允许服务人员使用的必要联系，默认空；notes由发起人明确编辑，不自动附整段目标或模型稿。额外允许`requester_display_name`作为发起人已明确提交的称呼，默认不暴露账号用户名。existing_record仅在经办有权且必要时另给引用，不对executor提供原台账。

`entry_permission={status:'unknown'|'reported_permission',note?:string}`只表示原述许可信息。公共区域也不默认为可进入；私有房间未知可提交/分派，但醒目标“进入许可待核，不能据此入室”。有声明也不称专业核准。access_window未知为空而非任意时间，排期/优先级由实际经办说明，模型不规定响应时限。cleaning的request_kind仅temporary/routine_ref/unknown；临时需求不改例行任务。repair不提供AI安全诊断或危险维修指令。

提交形成不可变投影快照并绑定`input_revision`。原事实更改后旧快照标stale，保留旧结果；发起人明确“更新服务需求”才建立新快照。地点、问题/范围、进入许可或时段等服务字段变化需重新确认安排：撤旧executor可读/写权、增assignment_epoch，待经办改派或重新确认，不能以原接受替新范围接受。无关私有来源变化不扩大投影；未能精确判影响时保守标待核但不覆盖旧历史。

## 3. 独立状态与合法推进

账号操作产生真实**软件动作记录/本人声明**，不证明现场已经执行。真实状态分开，不设置一个泛化completed按钮。

| 轨道/固定值 | 触发与限制 |
| --- | --- |
| `assignment`: unassigned/assigned/withdrawn | 发起人提交后unassigned；选定clerk手动分派assigned；改派增加epoch保留原分派；发起人撤回服务共享或clerk撤派为withdrawn，不表示实际工作已停止 |
| `acceptance`: pending/accepted/declined | 分派后pending；当前executor本人接受accepted或拒接declined（可说明原因）；拒接不算完成，等待经办改派 |
| `execution`: not_reported/in_progress/blocked/claimed_done | 本人accepted后可开始或报告障碍；claimed_done必须附非空真实处理说明，可附发生时间；只称“执行者声明已处理”，不改发起人结果/验收/关闭 |
| `requester_result`: unknown/unverified/resolved/still_problem | 发起人本人可记录未验证/解决/仍有问题；允许在尚无执行声明时如实反馈并显示与现记录差异；不得反推executor已处理或替专业验收 |
| `inspection`: unknown | 首切片Q-007专业验收范围/责任/凭据未冻，固定unknown；可保存经办提供的验收原话/凭据候选，不显示已通过或AI验收 |
| `closure`: open/waiting_rule | 未办结open；已处理声明/发起人解决仍不能正式闭单，显示waiting_rule与待核口径。闭单接口返回409 contract_unconfirmed；不以未回复、超时或保存稿自动完成 |

清洁的执行者声明与发起人反馈同样分开；其闭单服务口径也未冻，不套专业维修规则或新增主管验收。Q-007/清洁关闭标准未来核实后，只补明确专业要求、实际验证者/凭据及闭单条件。当前用户可以暂停助理、人工接手、结束准备目标或归档自己的视图，不改变服务业务闭单状态。

发起人still_problem或新问题不是把历史claimed_done删回未做；经办点“重新安排”建立新epoch并记录原因，可重新给原executor或改派他人，acceptance回pending、当前execution回not_reported，旧结果保留历史。所谓重复需求只提示关联候选，不能按相似文字合并或代本人取消。

## 4. 可直接实现的接口与持久化

只增加一个具体服务记录索引 `service_cases`，不建物业ERP或新岗位库：`id,matter_id UNIQUE,requester_id,clerk_id,executor_id?,input_revision,projection_json,sharing_status,assignment_epoch,version,assignment_status,acceptance_status,execution_status,requester_result,inspection_status,closure_status,updated_at`。sharing_status固定shared/withdrawn，区分发起人撤共享（经办也失权）与经办仅撤派（经办仍有权）。投影/状态JSON使用上述固定schema，事件仍写既有events为`service_event`固定JSON：`service_id,assignment_epoch,command,actor_id,recorded_by,evidence_class,occurred_at?,note?,before/after`；recorded_by是session actor，外部代录实际陈述人另存，不覆盖actor。索引仅需requester_id/clerk_id/executor_id及当前sharing/assignment状态；事务约束每服务一个当前executor。withdrawn后再次submit只由原owner明确重启共享、替换快照、增加epoch，复用同一服务ID，旧历史保留。

原事项不转owner。专用服务方法按requester/clerk/currentexecutor授权查询此小表，禁止为跨账号执行临时伪造Store actor=原owner。向原事项写事件可以在专用事务中显式matter_id/actor_id，但不能经owner上下文返回私有detail。主事项revision/control_epoch与服务version/epoch分别校验，事件不无故重写所有已确认事实。迁移使用现有SQLite一致备份/事务/引用检查，只增本表及索引，不改历史人工成果。

所有写接口需登录、当前会话CSRF、Idempotency-Key；事务内复核账号活跃/职责及对象范围，版本冲突409保留用户原输入。同键回放先核当前访问权，不能给已撤权账号返回原快照。下面路由名作为本切片约定，允许Leader统一命名但不得省掉版本及actor校验：

| 接口 | 请求/返回与授权 |
| --- | --- |
| `POST /api/matters/{id}/service/submit` | owner；`{expected_version,input_revision,clerk_id,contact?,notes?,entry_permission?}`；程序从已确认字段生成快照，返回201 service投影/version/epoch；重复同键一条服务 |
| `GET /api/services` / `GET /api/services/{id}` | 请求主体按requester/clerk/currentexecutor过滤，只返回必要投影、各轨、本人可见事件、下一步；executor列表不包含旧改派任务正文 |
| `POST /api/services/{id}/assign` | 选定clerk；`{expected_version,executor_id,note?}`；活跃executor、事务增epoch、撤旧executor权限、接受回pending；当前状态不自动接受。已有分派仍再assign须带改派原因 |
| `POST /api/services/{id}/respond` | 当前executor；`{expected_version,assignment_epoch,command,note?,occurred_at?}`；command accept/decline/start/blocked/claimed_done；start/blocked/claimed_done需已接受，blocked/claimed_done需说明；返回200安全service结果 |
| `POST /api/services/{id}/result` | requester；`{expected_version,assignment_epoch,result,note?}`；result unverified/resolved/still_problem，仍有问题可说明；不改执行轨 |
| `POST /api/services/{id}/revise` | requester；`{expected_version,input_revision,note}`；明确采用新已核服务字段；版本/epoch更新，旧接受失效，等待经办重新安排 |
| `POST /api/services/{id}/withdraw` | requester可撤服务共享；选定clerk可撤派；`{expected_version,note}`；撤派只撤executor，撤共享同时撤clerk/executor；记录区别和撤回前已执行声明 |
| `POST /api/services/{id}/statement` | 有当前服务访问权的requester/clerk；`{expected_version,reported_by,note,evidence_refs?}`；仅代录声明/凭据候选，不能推进承接/处理/本人结果轨；不伪装executor登录 |
| `POST /api/services/{id}/close` | 已可读者；现阶段一律409 contract_unconfirmed，明确等待实际关闭/验收口径；没有权限者先404，不泄漏服务存在 |

## 5. 改派、撤回、暂停与最短验证

改派同一事务切换executor、增epoch；两经办/重复操作不产生两名当前有效执行者。旧executor已保存声明留历史，但后续读取/回应一律404或409，不更新当前轨；客户端保留尚未保存的真实反馈文字，可经原渠道交当前经办按statement代录，不抹已发生事实。账号停用立即撤其可用动作；task仍保留待经办处置，不自动指定替代者。

暂停/人工接手只停止未来AI准备（沿原control_epoch取消pending/旧后台发布），不等于撤派、取消服务或阻止获授权本人登记已经发生的事实。人工提交/分派是显式软件动作，本切片不做模型自动分派/催问；暂停后仍可本人respond/result，确需撤派单独withdraw。所有变更活动显示做了什么、正在等哪一实际账号、下一步，不能用AI通知/已读当承接。

撤共享后clerk/executor列表、直接ID、旧投影/事件、来源/成果下载、缓存、幂等回放都失权；requester保留原事项与已存历史。后台若用服务投影准备需带actor/auth_epoch/service_version/assignment_epoch/access_snapshot，外部调用和写回前均核授权，失配停止，不借owner身份继续。

最短工程验收（隔离账号，尚未执行）：

1. repair/cleaning文字分别建事项→必要字段→提交选定clerk；无照片/主管审批可开始，私房许可未知显式待核。clerk/executor读原matter/source/artifact返回404，只看固定服务投影。
2. admin/未获交办clerk/其他executor不能分派或反馈；clerk不能替executor接受，executor不能替发起人解决。发起人resolved、executor claimed_done、专业验收unknown分别读回，close仍409。
3. 同键submit/respond不重复事件；旧版本409。改派后旧executor/旧epoch不能影响新分派，新executor需重新接受；原处理声明与改派原因保持历史。
4. blocked/declined/still_problem分别有明确等待对象与下一步；再次安排不删除已存事实。暂停后AI动作停止，但有权本人能登记实际反馈；withdraw独立撤权且不标实际已停止。
5. 撤共享/停用账号后列表、直接ID、旧投影、下载、回放及后台写回不泄漏；保存的人工成果完整。迁移前备份可读、失败回滚不清库。

正式闭单/专业验收、现场职责映射、生产权限与真实维修/清洁成效仍未验证；只卡对应正式结论，不把准备、独立账号软件承接和本人声明记录全部停住。此切片完成也不代表完整PRD或最终目标达成。
