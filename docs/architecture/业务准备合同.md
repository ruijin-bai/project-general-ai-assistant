# 多业务准备合同

2026-10-08 / V0.1。架构交付，供 Leader 实现与集成；本文不是功能完成、真实办理或业务验收记录。

基线：[PRD](../product/PRD.md)第4.2、6–10节及AC-020–025/031–033/037；[架构方案](架构方案.md)第4–5、10节；用户本轮持续开发完整竞赛版授权。本文只补 repair/cleaning/menu/feedback/leave/document/meeting/expense/inventory/hr 的文字准备合同，不改正式业务规则，不取代全部PRD。

## 1. 共用合同与当前差异

核实当前 `assistant_app/preparation.py` 与 `assistant_app/store.py`：六表已支持目标、事实修订、来源、成果、动作与事件；固定 `FIELDS` 是六个行程字段，`matters.domain` 只允许 travel/general，详情返回固定出行四轨。新增业务必须采用按业务的字段、轨道和成果注册表，不能将报修、菜单等继续套出行事实或四轨。

所有业务均由非空 `goal_text` 开始，允许先保存原话再补必要缺项；下文“必要”只影响准备稿是否可用，不是创建门槛。缺项仍能生成明确待补的成果，返回 `preparation_status=needs_review`。本地核对齐备可标 `ready`，含义仅为准备材料可用。AI候选与本地经办确认分开；确认不自动成为员工本人确认、厨师发布、正式批准或实际执行。

继续使用六表，不建维修、人员、库存等总账。当前事实值沿用 `null|string`，每项至少 `{value,status}`，status 为 unknown/candidate/confirmed。字段键按业务固定白名单，未知字段拒绝；来源引用、来源记录人、实际陈述人及时间沿用现有 sources。缺少字段按 unknown 读回，不能用空列表、0、否表示已核无数据。下表包含仅在本次目标需要时启用的可选字段，不能一律要求全部填写。

`tracks` 使用按业务固定注册表，只读准备阶段的初始 unknown 与原因。登记真实结果时另走显式白名单事件，不走 facts/模型输出；至少保留轨道、结果类型、适用事实修订、实际反馈人、经办记录人、来源ID、事实发生时间与记录时间。已有事件表只有文本，需支持结构事件后才能实现可核真实状态；尚未接入前只显示未知及原话，不从文字自动判已发布、已接受或已处理。执行者声明与结果核对必须是不同事件。

成果使用现有 artifacts 的类型、正文、版本和 input_revision。所有场景正文包含：目标、已知/候选/待核事实、场景成果、来源范围、缺项/等待对象/下一步。保存与复制只改变软件成果状态，不改变业务轨。重整生成新候选成果，人工保存版本保留；后台发布继续受 revision/control_epoch 栅栏约束。暂按现有整份成果待重核保守处理，但不得覆盖旧稿；精确字段依赖仍是后续改进，不能声称已实现“仅受影响部分重核”。

## 3. 独立真实状态与等待对象

轨道键用于固定展示，不是每个业务新增一张表。准备层全部默认 unknown；只有符合权限、凭据及已冻业务口径的显式事件才推进。字段齐备、成果保存、暂停/恢复均不推进真实状态。

| domain | 独立轨道与允许区分的真实记录 | 未核时等待对象/禁止推断 |
| --- | --- | --- |
| repair | `assignment` 分派/拒接/转派；`acceptance` 承接/障碍；`execution` 实际处理声明；`requester_result` 解决/仍有问题/未验证；`inspection` 需验收/结果待核；`closure` 关闭/退回/重开 | 实际经办、维修者、报修人、必要专业责任人。Q-007未冻不自动关闭；未反馈不写解决 |
| cleaning | `assignment` 安排；`acceptance` 承接/障碍；`execution` 处理声明；`requester_result` 仍有问题/未验证/真实结果；`closure` 关闭/取消/重新处理 | 经办、清洁执行者、发起人；没有服务口径不猜响应时限、不自动满意；清洁结果不是维修验收 |
| menu | `publication` 厨师真实发布/修订/撤回；`preparation` 实际备餐；`serving` 真实供餐 | 厨师及食堂责任人；生成不是发布，菜单不是实供，菜单不直接产生库存动作 |
| feedback | `recording` 软件内意见保存/原渠道提交引用；`response` 厨师真实回应；`adoption` 下一菜单实际采用 | 厨师；无需强制回应或采纳才能结束单次软件反馈任务。本地代录不是本人账号提交 |
| leave | `leave_decision` 真实休假决定；`passport`/`visa`/`domestic_proof`/`nis_entry`/`nis_exit` 各自材料与回执；`movement` 真实离返；`meal` 餐次核对 | 人员、外事/人事实办人、实际签发者。每份材料分未提供/待办理/提交引用/回执待核/已核/失效/待重核；清单不关闭手续 |

| meeting | `booking` 会议室实际确认；`record_confirmation` 实际纪要核对；`action_acceptance` 行动真实承接；`action_result` 完成声明与核对 | 实际安排/参与/行动责任人；会议笔记无决定不填决定，无承接不填已分派 |

## 4. 计算与可追源明细

expense_lines/item_lines/actions_text 等首步允许保留可编辑文字，明确“未结构核对，不计算”。需要计算或行动逐项跟进时，六表仍可复用，但应给这些指定字段增加严格行schema，而不是让字符串/模型解释直接参加计算：

- 金额行：稳定行ID、项目、十进制金额字符串、币种、发生日期/期间、来源ID及原位置、确认状态；币种不同分别合计。币种缺失、非法小数/金额或期间不明阻断相应合计；不能把缺数当0。
- 物资行：稳定行ID、物品、十进制数量字符串、单位、期间/地点、来源ID及原位置、确认状态；单位不同不直接合并，不凭菜单估消耗或修改库存。
- 会议行动行：稳定行ID、行动原述、责任人与期限（允许未知）、来源ID及原位置；真实承接/执行声明/结果核对另记事件。更改纪要不改写历史接受者的真实反馈。
- 菜单意见：保留来源ID/原意见ID/原版本、日期餐别/菜品、真实反馈人范围；仅稳定ID相同可去重，同一句不同来源不自动当同一人。同人多条意见可归组，但不能虚构人数或多数。

计算用程序 Decimal 或等价精确表示；小数位、取舍/舍入、汇率、累计和去重口径未知时不提供正式汇总。已确认规则须绑定来源/版本，不新建默认财务或人事标准。
